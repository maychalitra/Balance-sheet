HANZO'S MONEY MAP — PRODUCT SPECIFICATION

1. PRODUCT PURPOSE

Hanzo's Money Map is a cheerful, private balance-sheet application for Hanzo, the owner's 11-year-old son. It helps Hanzo record money coming in and going out, understand his balance, and give each euro a simple job. Language is encouraging and child-friendly without hiding the real ideas of income, expenses, saving, investing, goals, and generosity.

The application is a Vite, React, and TypeScript single-page app. Supabase is the only persistent store for financial records and plan settings. The app requires an internet connection for initial loading and all writes. Currency is fixed to EUR.

The visual direction remains a warm notebook-inspired working dashboard with cream paper, dark green text, yellow highlights, rounded cards, clear grouping, and distinct colors for the five money jobs.

2. PRIVATE FAMILY ACCESS

- Exactly one family account is pre-created and confirmed by an adult in Supabase Auth.
- The app supports email/password sign-in, remembered sessions, sign-out, reset-email requests, and choosing a new password after following the recovery link.
- There is no public registration interface.
- The Supabase publishable key may be present in the browser. Secret and service-role keys must never be included in frontend code or environment files intended for the browser.
- All database tables use Row Level Security. Authenticated users can select, insert, update, and delete only rows whose user_id equals auth.uid(). Anonymous users receive no table or RPC access.

3. PRIMARY DASHBOARD

After authentication and cloud loading, the first screen shows:

- Money I have: total income minus total expenses.
- Money in: the sum of all income entries.
- Money out: the sum of all expense entries.
- A deterministic smart money note based on current data.
- The five-job money plan and cumulative suggested amount for each job.
- Big Goal progress.
- A form for adding or editing an income or expense.
- Hanzo's Monthly Money Story with a weekly running-balance chart.
- A newest-first history of saved money moves.
- Controls for cloud refresh, backup, restore, background color, plan settings, and sign-out.

4. FIVE-JOB MONEY PLAN AND BIG GOAL

The recommended allocation is:

- Long-term investment: 20%. Money to grow for the future with an adult. The app explains that investments can rise or fall and does not recommend products.
- Big goal: 30%. Money for a specific goal that matters to the child.
- Planned spending: 30%. Purchases the child thinks about before buying.
- Fun now: 10%. Guilt-free money the child can enjoy without overthinking.
- Giving: 10%. Gifts, helping another person, or supporting a chosen cause.

The allocation is guidance calculated from total income and does not represent separate bank accounts. An adult can edit all percentages. Values must be whole numbers from 0 through 100 and total exactly 100. “Use recommended plan” restores 20/30/30/10/10.

When a valid income is entered, the form previews its exact split. All monetary calculations use integer euro cents. Rounding remainders are distributed deterministically so displayed parts always add to the original amount.

The goal name is optional and limited to 60 characters. The optional target is from EUR 0.00 through EUR 1,000,000,000.00 with at most two decimals. Progress equals cumulative Big Goal allocation divided by the target and is visually capped at 100%.

5. MONEY MOVES

Each transaction contains:

- id: unique non-empty text, at most 120 characters.
- user_id: the authenticated family owner.
- date: a real ISO date in YYYY-MM-DD form, not later than today.
- type: income or expense.
- amount: positive integer euro cents, at most 100,000,000,000 cents.
- category: one category recognized for the selected type.
- note: optional plain text, at most 120 characters.
- createdAt and updatedAt: cloud timestamps.

Income categories: Allowance, Chore, Gift, Sale, Other.

Expense categories: Food & Drink, School, Transport, Planned Purchase, Fun, Giving, Goal Purchase, Other.

The child can add, edit, and delete transactions. Editing keeps the original ID and creation time. Deleting requires confirmation. The history sorts by date newest-first and then creation time, and it can be filtered to all moves, income, or expenses.

Writes are remote-write-first: the UI reflects a mutation only after Supabase confirms it. Buttons prevent duplicate submissions while a request is pending. Concurrent edits use last successful write wins.

6. MONTHLY MONEY STORY AND CALCULATIONS

- The current month opens by default. Arrows navigate months, future months are blocked, and “This month” returns to the current month.
- The month displays income, expenses, and total account balance after that month's moves.
- A responsive line chart begins with balance carried into the month and plots the closing balance after every Monday-through-Sunday calendar week clipped to the month.
- The chart has week and EUR labels, directly labelled points, an accessible title, a complete text summary, and a clear empty-month message.
- Weekly chapters show date range, money in, money out, closing balance, and expandable transaction lines.
- The current week opens by default for the current month. A past month opens its latest week containing entries.

Totals, allocation splits, goal progress, chart balances, and all comparisons use integer cents. Visible values use EUR formatting with two decimal places.

Smart notes cover no entries, spending above income, goal completion, Fun spending above guidance, Giving, planning income before spending, low overall spending, and a general goal-reflection prompt.

7. SUPABASE DATA MODEL

money_map_settings contains one row per auth user with currency, five allocation percentages, goal name, target cents, a background theme, and updated timestamp. Database checks enforce EUR, percentage ranges and total, goal length, target range, and one of the supported background themes.

transactions uses a composite user_id/id primary key. Database checks and a trigger enforce ID length, non-future date, type, amount range, type-specific category, note length, and timestamps. An index covers owner, date descending, and creation time descending.

Both tables enable RLS with explicit select, insert, update, and delete policies for authenticated owners. Grants are revoked from anonymous users.

The authenticated reset_money_map RPC atomically deletes the owner's transactions and restores default settings. The authenticated replace_money_map RPC validates a complete version 1 backup and atomically replaces only the caller's rows. Both use auth.uid(), run with invoker rights, and cannot be executed by anonymous users.

8. CLOUD LOADING, CONNECTION FAILURE, AND BROWSER STORAGE

- On authentication, the app creates the default settings row if needed and fetches settings and transactions from Supabase.
- Supabase remains authoritative. Reloading the page always fetches cloud data.
- Manual Refresh retrieves current settings and transactions. Realtime subscriptions are not used.
- If loading fails before data is available, the app shows a retry and sign-out screen.
- If the connection fails after data loads, the last loaded data remains visible only in React memory, write controls are disabled, unsent form input remains, and the user can retry.
- Financial data and drafts are never persisted in localStorage, sessionStorage, IndexedDB, or Cache Storage.
- The obsolete localStorage key kidMoneyTracker.v1 is removed on startup and its former contents are not imported.
- Supabase Auth may persist only its login session so the family remains signed in.

9. BACKUP, RESTORE, AND CLEAR

Backup export downloads readable version 1 JSON named hanzo-money-map-backup-YYYY-MM-DD.json. The JSON retains the established EUR-decimal backup contract even though runtime and database calculations use cents.

Restore accepts JSON files no larger than 1 MB and no more than 10,000 transactions. The complete file is validated in the browser for version, currency, allocation, goal, unique IDs, dates, types, amounts, categories, notes, and timestamps. Confirmation is required. The PostgreSQL RPC repeats authoritative validation and replaces data inside one transaction so invalid input or any failure leaves existing cloud data untouched.

Clear everything requires confirmation and calls the atomic reset RPC. It restores recommended allocation, an empty goal, and no transactions.

10. ACCESSIBILITY AND RESPONSIVE BEHAVIOR

- Use semantic headings, sections, forms, fieldsets, labels, buttons, lists, progress semantics, SVG titles, and native details/summary disclosures.
- Provide a skip link and visible keyboard focus.
- Every input has a visible label; icon-only mobile actions retain accessible names through button text/title.
- Validation errors use plain language, an alert region, and focus the field needing attention.
- Success feedback uses a polite live region. Connection failure uses an alert.
- Controls are at least 44 pixels high where they are primary touch targets.
- The layout stacks without horizontal page scrolling on narrow screens and keeps the money plan beside the entry form on desktop.
- Respect prefers-reduced-motion.

11. ACCEPTANCE CRITERIA

- The pre-created user can sign in, remain signed in across refresh, sign out, request password recovery, and set a new password. There is no sign-up flow.
- Anonymous users and a different authenticated user cannot access the family rows or RPC operations.
- All existing dashboard calculations and workflows remain correct after migration to cents and Supabase.
- Adding, editing, deleting, settings updates, restore, and reset are visible only after successful cloud confirmation.
- Failed cloud operations preserve input and do not display unsaved changes as committed.
- Refresh loads changes made on another device. Changes are not pushed live.
- Awkward-cent allocation splits always add to the exact source income.
- Monthly calculations work across week, month, and year boundaries.
- Backups round-trip through export and atomic restore; malformed data cannot replace current data.
- No financial data is written to browser persistence; the retired storage key is removed.
- Unit tests and the production build pass, and the app remains accessible and usable on narrow mobile and wide desktop layouts.

12. DELIVERY

Deliver the React/Vite source, package lock, Supabase migration, tests, README setup instructions, and this specification. Keep the project local. A future static host may serve the built dist directory after its HTTPS URL is added to Supabase Auth redirect settings.
